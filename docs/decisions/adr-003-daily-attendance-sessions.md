# ADR-003: Daily attendance sessions and transactional checkout

- Status: Accepted
- Date: 2026-08-03

## Context

Students must register their arrival at the Hort before they can leave through
the checkout process. Arrival is supervised and recorded by an authenticated
Hort worker. The legacy checkout API searches all students, has no attendance
precondition, uses server-local `LocalDateTime`, and does not prevent duplicate
checkout operations transactionally.

The Hort operates on a local business day. UTC calendar dates cannot represent
that day reliably around midnight in Germany. The current application is not
in production, so the new invariant can be introduced without supporting
historical attendance reconstruction.

## Decision

### Attendance lifecycle

Each student may have exactly one attendance session per Hort business day:

```text
ABSENT --check-in--> PRESENT --check-out--> CHECKED_OUT
```

- A second check-in on the same business day is rejected, including after the
  session was checked out.
- Checkout requires an existing `PRESENT` session and closes that exact session.
- Returning after checkout is not supported. A future requirement may introduce
  multiple numbered sessions without changing historical records.

### Time semantics

- The initial Hort business timezone is `Europe/Berlin`.
- `attendanceDate` is calculated by the backend in that timezone.
- Check-in and checkout timestamps are generated by the backend and stored as
  PostgreSQL `TIMESTAMP WITH TIME ZONE` values representing UTC instants.
- API v1 exposes timestamps as ISO-8601 `OffsetDateTime` values.
- A future per-Hort timezone can replace the initial constant behind the same
  application boundary.

### Persistence and transaction boundary

- `attendance_session` owns the daily presence lifecycle and is tenant-owned.
- It records the student, business date, check-in instant/user/comment, and the
  optional checkout instant/user plus the related `check_out` row.
- A unique constraint on `(hort_id, student_id, attendance_date)` enforces one
  daily session.
- Checkout locks the attendance session, validates that it is still open,
  validates the selected authorization at the checkout instant, writes the
  checkout record and closes the session in one transaction.
- RLS and tenant-composite foreign keys protect attendance and checkout links.

### HTTP boundary and roles

The administrative API is rooted at `/api/v1/attendance`:

- `GET /check-in-candidates`
- `POST /check-ins`
- `GET /present-students`
- `POST /check-outs`

`HORT_ADMIN` and `ASSISTANT` may use these operations. `PARENT` has no access.
The authenticated worker is derived from the security context; neither tenant,
timestamps nor recorder identity are accepted from the request.

### Checkout authorization

- `PICKUP` requires a current, active PickupRight whose student and collector
  match the request.
- `SELF_DISMISSAL` requires the referenced active authorization. Daily rules
  must have reached their allowed time. Permanent rules must match the current
  weekday and allowed time.
- Revoked, scheduled, expired or mismatched authorizations are rejected.
- Conditional request variants use an explicit `method` discriminator rather
  than a nullable Boolean.

## Consequences

- Checkout search returns only students with an open attendance session.
- The web gains a separate *Anmeldung* workflow and *Abmeldung* consumes the
  presence API.
- Vollmacht onboarding must search `/api/v1/students`; it must not reuse the
  presence-filtered checkout search.
- Legacy `/api/checkout/*` was removed after the web migrated to attendance API
  v1, preventing callers from bypassing the daily-session precondition.
